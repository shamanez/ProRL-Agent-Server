ProRL Agent Server — System Overview

Contract-first agentic RL training fabric · Qwen3-4B on SWE-Bench · GRPO/DAPO · branch: producer-as-a-service

What This System Is

ProRL Agent Server is a scalable agentic reinforcement learning system that trains a language model to solve software engineering tasks by actually running code in a sandboxed environment, observing whether it works, and learning from the outcomes.

Instead of a single monolithic training loop, it is built as five independent services that communicate through stable contracts — each one can be replaced, scaled, or debugged without touching the others. Every boundary condition between services is tested and enforced in code.

What Each Service Does and Why It Exists

RolloutWorker
scripts/services/start_rollout_worker.sh

Reads tasks from the parquet dataset, dispatches N sibling episodes to ProRL via HTTP, collects completed episodes, builds TrainingSample objects, and pushes groups to the LiveStore.

Why separate? Decouples rollout speed from training speed. The trainer can sample whenever it's ready; the worker produces continuously. In future, multiple workers can fan out across different environments or machines with zero trainer changes.
  • Zero VERL or OpenHands imports (BC-13)
  • Owns the parquet dataset — trainer never sees file paths (BC-14)
  • Reads one PolicyVersionSnapshot per group so all N siblings use the same policy version (BC-0)
EnvironmentProvider
ProRL FastAPI :8006 · scripts/_internal/s0_prorl.sh

Receives POST /process from the worker, manages a full multi-turn agent loop inside a Singularity sandbox, calls vLLM for each assistant turn via /v{N}/generate, and returns the completed episode with token IDs and per-token logprobs.

Why separate? All sandboxed execution lives here — file systems, Docker/Singularity containers, tool calls. The worker never knows how tasks are executed. Swap ProRL for GEM or ORS by implementing the same HTTP contract.
  • Token-in / token-out invariant enforced here — never decodes and re-tokenizes (BC-1)
  • Frozen through S4 — unchanged from the original implementation
InferenceBackend
vLLM Pool :8100-8103 on EC2 · scripts/serving/launch_remote_vllm_pool.sh

Four vLLM child processes on a remote GPU host. Receives token-ID prompts, returns token-ID responses with logprobs. Each child supports path-versioned pinning: /v{N}/generate pins a trajectory to policy version N for its full duration.

Why pinning? Without it, a trajectory could start on policy v5 and finish on v6 mid-episode — the behavior_policy_version stamp would be wrong, the IS correction would use incorrect weights, and training would silently diverge. Pinning is the correctness invariant (BC-10).
  • LoRA slots managed with LRU eviction (--max-loras 8)
  • 409 response = version already loaded (idempotent)
  • Any non-200/409 on /reload_lora → hard abort (BC-9)
LiveStore
gRPC Unix socket /tmp/prorl_live_store.sock · scripts/services/start_live_store.sh

A bounded in-memory FIFO of training groups. The worker pushes groups in; the trainer pops groups out. get_batch blocks server-side until enough fresh groups are available — no busy-polling on the trainer side.

Why a separate service? The trainer and the worker run at different speeds. The LiveStore is the clock-separation buffer: the worker pushes as fast as ProRL produces episodes; the trainer samples on its own cadence. Without it, one slow ProRL episode would stall the whole training step.
  • Pop-on-sample — consumed groups are gone (no duplicate gradients, BC-3)
  • Staleness eviction by created_at_step — old groups dropped automatically
  • No-progress detector: raises NoProgressError after 90 min of no pushes (BC-5)
PolicyRegistry
gRPC Unix socket /tmp/prorl_policy_registry.sock · scripts/services/start_policy_registry.sh

Receives publish_policy_version from the trainer, fans out /reload_lora to all vLLM pool children, writes the manifest file for worker polling, and notifies gRPC streaming subscribers. Single source of truth for active policy versions.

Why not let the trainer fanout directly? The trainer has one job: compute gradients. The PolicyRegistry owns the LoRA distribution contract — if any pool child fails to ACK, it raises PublishFailedError and the trainer aborts (BC-9, §3.3). A partially-upgraded pool means different trajectories use different weights, making IS correction incorrect.
  • SQLite publish history for audit and recovery
  • Writes manifest file → worker polls at 1Hz → PolicyVersionCache swaps atomically (BC-7)
TrainerAdapter
VERL FSDP inside Docker · scripts/_internal/s3_fullasync_docker.sh

Calls LiveStore.get_batch(), pads the unpadded samples locally, computes GRPO/DAPO advantages, runs the FSDP optimizer step, saves a LoRA checkpoint, and calls PolicyRegistry.publish_policy_version(). That is all it does.

Why no dataloader, no producer? The trainer knowing about the dataset or the rollout manager couples it to a specific environment. By being a pure consumer of the LiveStore, the trainer can be swapped for ROLL or slime with zero changes to any other service. You only need to implement the same get_batch call.
  • Connects only to LiveStore and PolicyRegistry (BC-15)
  • No parquet files, no ProRL address, no vLLM address
  • 8× A100 FSDP with rank-16 LoRA

The Five Rules That Cannot Be Broken

RuleWhat it protectsWhat breaks if violated
BC-0 / §3.2
One policy snapshot per group		 All N sibling episodes in a GRPO group dispatch with the same behavior_policy_version Siblings generated on different policies → mixed advantages → incorrect group-relative normalisation → NaN loss
BC-1 / §3.1
Token IDs, never strings		 Every wire field carrying model output uses list[int], never decoded text Re-tokenizing shifts token boundaries → actor and reference diverge → KL/entropy NaN within 2 steps
BC-9 / §3.3
Abort on partial publish		 Every vLLM child must ACK /reload_lora before policy_version increments Mixed-version pool → some trajectories run on old policy, some on new → IS correction uses wrong weights → silent training corruption
BC-13
Worker has zero VERL/OpenHands imports		 RolloutWorker is a standalone Python process with only HTTP and gRPC dependencies Coupling worker to VERL means swapping the trainer also requires rewriting the worker — pluggability collapses
BC-15
Trainer connects only to LiveStore + PolicyRegistry		 The trainer has no dataset, no producer thread, no ProRL or vLLM address Trainer sneaks back into being the orchestrator — adding a second trainer or a new environment requires rewriting the trainer

How to Start a Training Run — Step by Step

Source credentials and set data path

All scripts source this file. It sets REMOTE_DNS, WANDB_API_KEY, and Singularity Docker credentials.

source /home/ubuntu/.prorl_creds.env

# Point the worker at the SIF-filtered dataset
export DATA_FILES=/home/ubuntu/data/SkyRL-v0-293/train.ready.parquet

Build Singularity images (one-time per new environment)

SWE-Bench tasks run inside Singularity containers. The 232 GB OCI layer cache is pre-downloaded — conversion takes ~4 min per image with no network.

# Build first 10 images for a diverse initial dataset
CACHE=scripts/_singularity_cache
mkdir -p $CACHE/apptainer_tmpdir $CACHE/apptainer_localcachedir

APPTAINER_CACHEDIR=$CACHE/apptainer_cachedir \
APPTAINER_TMPDIR=$CACHE/apptainer_tmpdir \
APPTAINER_DOCKER_USERNAME=$SINGULARITY_DOCKER_USERNAME \
APPTAINER_DOCKER_PASSWORD=$SINGULARITY_DOCKER_PASSWORD \
SINGULARITY_DOCKER_USERNAME=$SINGULARITY_DOCKER_USERNAME \
SINGULARITY_DOCKER_PASSWORD=$SINGULARITY_DOCKER_PASSWORD \
poetry run python scripts/pull_swe_images.py \
  --parquet-file /home/ubuntu/data/SkyRL-v0-293/train.parquet \
  --dest-dir singularity_images \
  --start-index 1 --end-index 10

Filter the dataset to only tasks with built images

This produces train.ready.parquet containing only rows whose Singularity image exists. Re-run any time more images are built.

poetry run python scripts/_internal/filter_parquet_to_built_sifs.py \
  --source /home/ubuntu/data/SkyRL-v0-293/train.parquet \
  --sif-dir singularity_images \
  --dest /home/ubuntu/data/SkyRL-v0-293/train.ready.parquet \
  --min-rows 1

# Output: [INFO] 10/293 rows survive filter → OK to proceed

Start the InferenceBackend (remote vLLM pool)

Launches 4× vLLM child processes on the EC2 vllm-instance host. Takes ~2 min for the model to load. The SSH alias vllm-instance must exist in ~/.ssh/config.

bash scripts/serving/launch_remote_vllm_pool.sh start

# Verify all 4 ports healthy:
for port in 8100 8101 8102 8103; do
  curl -sf http://$REMOTE_DNS:$port/health && echo ":$port OK"
done

Start the EnvironmentProvider (ProRL)

Starts the ProRL FastAPI server. vLLM addresses are baked in at startup — they survive restarts without manual re-registration.

nohup bash scripts/_internal/s0_prorl.sh > /tmp/s0-prorl.log 2>&1 &

# Wait for healthy:
curl -sf http://localhost:8006/status     # → {"status":"running"}
curl -sf -X POST http://localhost:8006/start -H 'Content-Type: application/json' -d '{}'

Start LiveStore and PolicyRegistry (run in parallel)

Both use Unix domain sockets under /tmp/. The -v /tmp:/tmp mount in the trainer's Docker run makes them visible inside the container.

PYTHON=/home/ubuntu/.cache/pypoetry/virtualenvs/openhands-ai-342rfuwh-py3.12/bin/python

# LiveStore
nohup $PYTHON -c "
import logging,signal,sys; sys.path.insert(0,'.')
logging.basicConfig(level='INFO')
from live_store.server import serve
s=serve(socket_path='/tmp/prorl_live_store.sock',max_size=256,
        staleness_cutoff_k=4,no_progress_timeout_s=1800)
signal.signal(signal.SIGTERM,lambda s,f:(s.stop(grace=2),sys.exit(0)))
s.wait_for_termination()
" > /tmp/live_store.log 2>&1 &

# PolicyRegistry (replace REMOTE_DNS with actual value)
nohup $PYTHON -c "
import logging,signal,sys; sys.path.insert(0,'.')
logging.basicConfig(level='INFO')
from policy_registry.server import serve
s=serve(socket_path='/tmp/prorl_policy_registry.sock',
        db_path='/tmp/prorl_policy_registry.db',
        pool_endpoints=['http://${REMOTE_DNS}:8100','http://${REMOTE_DNS}:8101',
                        'http://${REMOTE_DNS}:8102','http://${REMOTE_DNS}:8103'])
signal.signal(signal.SIGTERM,lambda s,f:(s.stop(grace=2),sys.exit(0)))
s.wait_for_termination()
" > /tmp/policy_registry.log 2>&1 &

# Wait for sockets:
until [[ -S /tmp/prorl_live_store.sock ]]; do sleep 1; done  && echo "LiveStore ready"
until [[ -S /tmp/prorl_policy_registry.sock ]]; do sleep 1; done  && echo "PolicyRegistry ready"

Start the RolloutWorker

The worker begins generating episodes immediately. It cycles through train.ready.parquet, dispatches groups to ProRL, and pushes completed groups to the LiveStore. No filtering at this stage — all groups flow through.

nohup $PYTHON -m rollout_worker.main \
  --live-store-socket /tmp/prorl_live_store.sock \
  --prorl-url http://localhost:8006 \
  --policy-id qwen3-4b-skyrl \
  --environment-id swe_agent \
  --data-files /home/ubuntu/data/SkyRL-v0-293/train.ready.parquet \
  --group-size 4 \
  --archive-disabled \
  > /tmp/rollout_worker.log 2>&1 &

# Monitor — wait for first group push before starting trainer:
$PYTHON -c "
import sys,time; sys.path.insert(0,'.')
from live_store.client import LiveStoreClient
cli=LiveStoreClient('/tmp/prorl_live_store.sock',
    policy_id='qwen3-4b-skyrl',environment_id='swe_agent')
while cli.total_pushes() == 0: time.sleep(10)
print('LiveStore warm — trainer can start')
cli.close()
"

Start the Trainer — this is the main training script

This script starts the Docker container, installs dependencies, health-checks the vLLM pool, and launches the FSDP training loop. The trainer reads from the LiveStore, computes GRPO advantages, updates LoRA weights, and publishes via the PolicyRegistry at every step (SAVE_FREQ=1).

# ── THE MAIN TRAINING COMMAND ──────────────────────────────
bash scripts/_internal/s3_fullasync_docker.sh \
  data.train_files=[/data/SkyRL-v0-293/train.ready.parquet] \
  data.val_files=[/data/SkyRL-v0-293/train.ready.parquet]

# Optional overrides (all have sensible defaults):
BATCH_SIZE=4               # groups per step  (32 for production)
TOTAL_TRAINING_STEPS=500   # stop after N steps
SAVE_FREQ=1                # publish LoRA every step
USE_TEMPORAL_IS=False      # IS correction for stale groups

Training logs stream to /tmp/s3-fullasync.log. Look for training/global_step:N in the log to track progress.

Or: start everything with one command

The orchestrator script runs all six steps in the correct order, health-probing each service before starting the next, and waits for the LiveStore warm-up gate before launching the trainer.

DATA_FILES=/home/ubuntu/data/SkyRL-v0-293/train.ready.parquet \
bash scripts/services/start_all.sh

Stop in reverse order: trainer → worker → LiveStore + PolicyRegistry → ProRL → vLLM pool.
