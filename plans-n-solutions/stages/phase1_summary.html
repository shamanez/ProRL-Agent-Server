Phase 1 — Closed-loop LoRA publish to a remote vLLM pool

Trainer (FSDP, 8×A100) and the rollout engine (vLLM, 4 children on a separate EC2 box) run on independent clocks. After every save_freq training steps, the trainer extracts a rank-16 LoRA adapter from its FSDP checkpoint, ships it over HTTP to every pool child, and the child swaps it in-place with zero /generate downtime. The importance-ratio drift that unbounded stale rollouts cause is now capped by design.

The first step to bring TEEs for Decentralized RL is fully decoupled the Rollouts from the Trainer.

Why LoRA first

The baseline topology had a correctness hole: the pool's weights were loaded once and never updated. By step N the rollout policy was N updates behind the trainer, and GRPO's importance ratio πθ / πbehavior drifted open-loop (baseline wdqqu52k: ratio grew from 1.6 past 2.0 over 7 steps). Closing the loop with a full state-dict (~8 GiB bf16 for Qwen3-4B) would work but the protocol overhead dominates planning. LoRA gets the protocol right first at 60–70× less payload.

How the vLLM reload doesn't break anything

This is the hinge of the whole protocol. vLLM 0.18 exposes three capabilities we lean on:

  • AsyncLLMEngine.add_lora(LoRARequest) / remove_lora(lora_int_id) — in-place adapter install and eviction, no engine restart.
  • --max-loras N — GPU slot budget for concurrent adapters. We set N=2 so the prior and the new adapter coexist during the swap window.
  • Per-request lora_request= kwarg on engine.generate — the adapter a request is served under is pinned at request-start, not at token-generation time.

Built on top, the Phase 1 drain protocol keeps in-flight generates correct across a swap. The pool child runs FastAPI async handlers; /reload_lora and /generate can interleave arbitrarily. Correctness comes from two locks + one counter:

Why async matters here

With a synchronous handler, /reload_lora would have to queue behind every in-flight /generate on the same event loop — the ~14 s add_lora call would then block acceptance of new rollout requests entirely. Async FastAPI + AsyncLLMEngine lets the two handlers share the loop: add_lora yields to the scheduler while new generates continue to pick up the old adapter, and the moment active_lora flips, the very next request uses the new one.

Why in-place reload is a big deal

The naïve alternative is restart-on-publish: tear down the vLLM engine, reload the base model, re-seed the KV cache, re-pin CUDA buffers. That's 1–2 minutes per swap on Qwen3-4B. In-place add_lora reuses the hot base weights, hot KV cache, and hot scheduler state. We pay 11–14 s of adapter upload instead of a cold restart, and rollouts never stop — the pool's effective uptime is 100% across the swap.

Atomicity — what guarantees correctness

  • _swap_lock (asyncio.Lock) — only one /reload_lora in flight per child.
  • _inflight_cond (asyncio.Condition) — /generate snapshots active_lora and increments _inflight[lora_int_id] under the same cond, so the swap can't commit and start draining between the snapshot and the increment.
  • Drain blocks remove_lora(prior) until _inflight[prior]==0. On timeout we skip remove and return 502 — correctness over cleanup.
  • Trainer-authoritative policy_version. Partial fan-out failure = RuntimeError, run aborts — mixed-version batches are a correctness bug.

Failure modes that are now impossible

  • Request served against a half-loaded adapter: blocked by the atomic snapshot + increment.
  • remove_lora races ahead of a still-running generate: blocked by drain.
  • Pool child returns 200 while remove_lora silently failed: swap returns 502; trainer aborts.
  • Idempotent replay of the same publish bumping version twice: 409 path; trainer counts as success.

Deployment context — why the numbers look the way they do

  • Same-region EC2. Trainer box and vLLM pool are in the same AWS region, so the 122 MiB tarball moves in ~2.0 s over the public DNS endpoint with no cross-region hop. Cross-region would push transfer latency by 10–100×.
  • Four children on one EC2 box. The pool is four independent vLLM processes on ports 8100–8103, each pinned to a distinct GPU, behind a shared orchestrator (launch_remote_vllm_pool.sh). The trainer's rollout_dp_size = world_size / TP_size = 8 / 2 = 4 matches that fan-out. Each publish POSTs in parallel to all four; the max endpoint is the wall clock.
  • Bare FastAPI, no Ray on the pool. The pool child runs AsyncLLMEngine directly under FastAPI. No Ray actors, no placement group. The trade-off is that Phase 2's full state-dict swap can't use Ray's collective_rpc path; it will need a per-child primitive.
  • Token-in / token-out wire format. /generate moves {prompt_token_ids, response_ids, logprobs} — never text. Preserves multi-turn token boundaries across adapter swaps; one of the invariants Phase 2 must also keep.

What comes next

Beyond Phase 1, three directions, roughly 100 words.

Replay buffer / truly async RL. Store trajectories keyed by policy_version; sampler draws under a staleness budget with clipped importance weights. Decouples rollout wall clock from training wall clock entirely.

Beyond LoRA. Phase 2 ships full state-dicts (~8 GiB) over the same publish protocol — motivated when rank-16 measurably caps reward.

Drift-triggered sync. Replace fixed save_freq with an adaptive trigger on a rolling rollout_corr/ppl_ratio EMA — publish when drift crosses a threshold, not on a wall-clock cadence.
